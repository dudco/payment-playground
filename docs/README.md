# 문서 가이드

이 디렉터리는 현재 동작하는 기준과 향후 기능 확장 과정을 함께 관리한다. 문서는 코드보다 앞서 합의된 계약을 남기되, 구현되지 않은 기능을 현재 계약처럼 상세화하지 않는다.

## 문서 구조

### `prd.md`

프로젝트의 제품 요구사항과 현재 MVP 범위를 정의한다.

- 사용자 흐름, 공개 API의 큰 계약, 상태 전이, 비범위, 수용 조건을 기록한다.
- 기능 추가로 사용자 흐름·공개 API·수용 조건이 바뀔 때 갱신한다.
- 세부 구현 클래스나 DB 컬럼은 여기서 결정하지 않는다.

현재 문서: [주문·결제 API PRD](prd.md)

### `data-model.md`

여러 기능이 공유하는 영속 데이터와 정합성 규칙의 현재 기준을 기록한다.

- 엔티티 관계, 핵심 필드, 금액·상태 무결성, 민감정보 보존 정책을 기록한다.
- 새 엔티티·필드·상태 전이·DB 제약이 필요할 때 갱신한다.
- 기능별 상세 요청·응답은 `specs/`에 둔다.

현재 문서: [주문·결제 데이터 모델](data-model.md)

### `adr/`

Architecture Decision Record의 모음이다. 되돌리기 어렵거나 여러 구현에 영향을 주는 기술적 결정을 짧게 기록한다.

- 결정 배경, 고려한 대안, 채택한 결론, 결과를 기록한다.
- 단순 구현 상세나 가변적인 TODO는 ADR로 만들지 않는다.
- 새 결정은 다음 번호 파일로 추가하며, 과거 ADR을 현재 결정에 맞춰 고쳐 쓰지 않는다. 기존 결정을 대체해야 하면 새 ADR에서 대체 관계를 명시한다.

현재 ADR:

- [ADR-0001: 결제수단별 Gateway 분리](adr/0001-payment-gateway-by-method.md)
- [ADR-0002: 멱등키 기반 Cart 초안에서만 주문 생성](adr/0002-cart-checkout-creates-order.md)

### `specs/`

기능별 기술 명세를 둔다. 하나의 기능이 독립적인 API 계약·상태 규칙·오류 처리·테스트 조건을 가질 때 새 문서를 만든다.

- 상단에 `상태`, `작성일`, `최종 갱신일`을 기록한다.
- 제목은 문서의 정체성을 유지하기 위해 날짜 없이 쓴다.
- 예: 분할 결제를 시작하면 `specs/split-payment.md`를 새로 작성한다.
- 기존 기능의 전체 흐름이 바뀌면 `prd.md`, `data-model.md`도 필요한 범위에서 함께 갱신하고 새 스펙 문서로 링크한다.

현재 스펙: [주문·결제 API 초안 명세](specs/order-payment-api.md)

### `plans/`

승인된 스펙을 실제로 구현하기 직전에 작성하는 실행 계획이다.

- 파일명은 `YYYY-MM-DD-<feature>-implementation.md` 형식을 사용한다.
- TDD 순서(RED → GREEN → REFACTOR), 정확한 대상 파일, 테스트 명령, 검증 기준을 기록한다.
- 계획은 구현 작업 단위이며, 기능 요구사항의 기준 문서는 `prd.md`와 `specs/`다.

현재 계획: [주문·결제 API 초안 구현 계획](plans/2026-09-13-order-payment-api-implementation.md)

## 새 기능을 추가하는 순서

1. PRD의 범위·사용자 흐름·수용 조건이 바뀌는지 확인한다.
2. 독립적인 기능이면 `specs/`에 새 초안 명세를 작성한다.
3. 공유 데이터나 상태가 바뀌면 `data-model.md`를 갱신한다.
4. 되돌리기 어려운 결정이 있으면 새 ADR을 추가한다.
5. 구현 직전에 `plans/`에 날짜가 포함된 TDD 계획을 작성한다.
6. 문서 검토 뒤 구현 코드와 자동 테스트를 같은 기능 PR에 추가한다.

예를 들어 분할 결제는 `specs/split-payment.md`를 새로 만들고, 복수 Payment의 금액 정합성과 주문 상태가 바뀌는 만큼 `prd.md`와 `data-model.md`를 함께 갱신한다. 결제 배분·부분 취소 정책이 장기 결정이라면 다음 ADR도 추가한다.
