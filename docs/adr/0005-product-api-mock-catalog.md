# ADR-0005: 상품 API는 코드 내 Mock 카탈로그로 제공

- 상태: 승인됨
- 일자: 2026-10-13
- 관계: 코드 이름은 [코드 컨벤션](../conventions.md)에 따라 `ProductCatalog` → `ProductRepository`, `MockProductCatalog` → `FixedProductRepository`로 바뀌었다(2026-10-16). 결정 내용은 그대로다.

## 맥락

장바구니는 상품을 참조하고, 상품명과 판매가로 금액을 계산한다. 이전 설계는 상품 카탈로그가 없어 클라이언트가 보낸 `productName`과 `unitPrice`를 그대로 믿었다. 이러면 서버가 계산한 합계도 클라이언트가 정한 가격에 의존한다.

반면 이 프로젝트의 관심사는 장바구니·주문·결제의 동시성과 정합성이다. 상품 등록·수정·노출 상태, `Product 1 : N Item`, 재고 같은 카탈로그 관리는 현재 실험 대상이 아니다.

## 결정

- 상품은 `ProductCatalog` 인터페이스로만 조회한다.

  ```kotlin
  interface ProductCatalog {
      fun findAll(): List<Product>
      fun findById(productId: String): Product?
  }
  ```

- 구현체는 코드에 고정된 상품 목록을 가진 `MockProductCatalog` 하나다. DB 테이블, Flyway 마이그레이션, Redis 키를 만들지 않는다.
- 공개 API는 조회만 제공한다: `GET /products`, `GET /products/{productId}`. 생성·수정·삭제 API는 만들지 않는다.
- 장바구니는 상품 ID와 수량만 저장하고, 상품명과 판매가는 응답할 때마다 `ProductCatalog`에서 읽는다. 클라이언트가 보낸 가격은 받지 않는다.
- 판매가는 KRW 정수(`Long`)다.

## 고려한 대안

### 대안 1: 클라이언트가 보낸 상품명·가격을 신뢰 (이전 설계)

- 장점: 상품 모델이 전혀 필요 없다.
- 단점: 가격을 서버가 통제하지 못한다. 장바구니 금액 계산이 의미를 잃는다.

채택하지 않는다.

### 대안 2: 상품을 SQLite 테이블로 영속화

- 장점: 실제 서비스 구조에 가깝고, 가격 변경을 데이터로 다룰 수 있다.
- 단점: 엔티티·마이그레이션·시드 데이터·관리 API가 필요하다. 지금 실험하려는 문제와 관련이 없다.

채택하지 않는다. 재고 차감이나 가격 변경 경합을 실험할 때 재검토한다.

### 대안 3: `ProductCatalog` 인터페이스 + 코드 내 Mock 구현

- 장점: 서버가 가격을 결정하면서도 구현이 가장 작다. 실제 저장소로 바꿀 때 인터페이스 구현체만 교체하면 된다.
- 단점: 상품 데이터를 바꾸려면 코드를 고치고 다시 배포해야 한다.

채택한다.

## 결과

- 장바구니 금액은 항상 서버의 현재 판매가로 계산된다.
- 테스트는 Mock 목록의 상품 ID를 그대로 사용한다. 상품 ID를 바꾸면 테스트와 스펙 예시도 함께 바꾼다.
- 장바구니에 담긴 뒤 가격이 바뀌면 다음 조회부터 새 가격이 보인다. 가격 스냅샷은 주문 생성 시점에 `OrderLine`으로 남기는 것으로 하고, 주문 스펙에서 확정한다.
- 상품을 영속화하는 시점에 이 ADR을 대체하는 새 ADR을 쓴다.
