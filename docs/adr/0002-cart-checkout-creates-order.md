# ADR-0002: 장바구니를 주문 생성의 유일한 출발점으로 사용

- 상태: 승인됨
- 일자: 2026-09-13

## 맥락

주문 전 고객이 선택한 복수 상품을 보존하고 조회할 수 있는 장바구니 API가 필요하다. 장바구니와 주문 모두 여러 라인을 가지므로, 이름과 생명주기를 분리하지 않으면 주문 전 변경 가능한 데이터와 주문 후 불변 기록이 섞일 수 있다.

## 결정

- `Cart`와 `CartLine`을 별도 엔티티로 둔다.
- 장바구니 생성은 `POST /carts`, 조회는 `GET /carts/{cartId}`로 제공한다.
- 주문은 `POST /carts/{cartId}/orders`로만 생성한다.
- 주문 생성 시 `CartLine`을 불변 `OrderLine`으로 복사한다.
- `Cart`는 `ACTIVE -> CHECKED_OUT`으로 한 번만 주문 전환할 수 있고, `Order.cartId`에 unique 제약을 둔다.

## 고려한 대안

### 대안 1: `POST /orders`가 주문 라인을 직접 수신

- 장점: API와 엔티티 수가 적다.
- 단점: 주문 전 상품 선택 상태를 조회하거나 보존할 수 없고, 장바구니 요구를 충족하지 못한다.

채택하지 않는다.

### 대안 2: 장바구니와 주문이 같은 라인 테이블을 공유

- 장점: 복사 로직이 없다.
- 단점: 장바구니의 가변 데이터가 결제·취소의 근거가 되는 주문 이력을 바꿀 위험이 있다.

채택하지 않는다.

### 대안 3: CartLine을 OrderLine으로 복사하여 주문 생성

- 장점: 장바구니는 결제 전 데이터, 주문 라인은 주문 시점 불변 스냅샷이라는 책임이 명확하다.
- 단점: 중복 데이터가 생긴다.

채택한다. 주문 당시 상품명·판매가·수량을 독립적으로 보존하는 것이 데이터 중복 비용보다 중요하다.

## 결과

- 주문 금액과 결제 금액은 `OrderLine`으로 계산한다.
- 이 MVP에서는 장바구니 생성·조회와 주문 전환만 제공한다. 장바구니 라인 수정/삭제, 만료, 고객당 활성 장바구니 단일화는 후속 기능으로 분리한다.
- `Product`, `Item`, `CartLine`, `OrderLine`의 명명이 겹치지 않으며, 추후 재고/매입 모델이 추가되어도 주문 이력과 분리된다.
