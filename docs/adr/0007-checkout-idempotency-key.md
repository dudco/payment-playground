# ADR-0007: 장바구니에서 발급한 체크아웃 멱등키를 주문·결제까지 사용

- 상태: 승인됨
- 일자: 2026-10-13
- 관계: [ADR-0002](0002-cart-checkout-creates-order.md)의 "멱등키는 Cart 초안의 식별자이자 주문 생성 재시도 키"를 대체한다. 장바구니 구조는 [ADR-0006](0006-cart-per-customer.md)을 따른다.

## 맥락

고객 한 명의 구매는 "장바구니 → 주문 생성 → 결제"로 이어진다. 네트워크 오류로 응답을 못 받은 클라이언트가 주문·결제 요청을 재시도하면, 서버는 그것이 재시도인지 새 구매인지 구분할 수 있어야 한다. 그렇지 않으면 주문이 두 번 생기거나 결제가 두 번 승인된다.

장바구니가 고객 ID로 식별되면서([ADR-0006](0006-cart-per-customer.md)) 멱등키는 더 이상 장바구니를 찾는 키가 아니다. 대신 "이 장바구니에서 시작된 한 번의 구매 흐름"을 가리키는 값이 필요하다.

## 결정

하나의 구매 흐름은 하나의 **체크아웃 멱등키**로 식별한다. 키는 장바구니에서 발급되어 주문과 결제가 같은 값을 쓴다.

```text
POST /cart (첫 저장)        → 서버가 idempotencyKey 발급, 장바구니에 보관
POST /cart (이후 변경)      → 같은 키 유지
POST /order                → Idempotency-Key: <key>   같은 키 재호출은 기존 주문 반환
POST /payments             → Idempotency-Key: <key>   같은 키로 승인된 결제가 있으면 그 결과 반환
```

### 장바구니 단계 (이번 스펙에서 구현)

- 장바구니가 처음 저장될 때 서버가 UUID를 발급한다. 클라이언트는 키를 지정할 수 없다.
- 장바구니가 존재하는 동안 내용이 바뀌어도 키는 유지한다.
- 장바구니가 사라지면(비우기, TTL 만료) 키도 사라지고, 다시 담으면 새 키가 발급된다.
- 키는 `GET /cart`, `POST /cart` 응답의 `idempotencyKey`로 클라이언트에 전달된다.

### 주문·결제 단계 (해당 스펙에서 확정할 제약)

아래는 이후 스펙이 지켜야 할 방향이다. 세부 계약은 주문·결제 스펙과 그때의 ADR에서 확정한다.

- **주문:** `POST /order`는 `Idempotency-Key` 헤더를 필수로 받는다. 현재 고객의 장바구니 키와 같아야 한다. 같은 키로 이미 주문이 있으면 새 주문을 만들지 않고 기존 주문을 반환한다. `orders.idempotency_key`는 unique다. 주문이 생성된 장바구니는 삭제해, 다음 구매가 새 키로 시작되게 한다.
- **결제:** `POST /payments`도 같은 키를 `Idempotency-Key`로 받는다. 키로 주문을 찾고, 그 주문에 이미 승인된 결제가 있으면 새로 승인하지 않고 기존 결과를 반환한다. 거절된 결제 뒤의 재시도는 허용한다.
- 주문 여부의 기준은 RDB(`orders.idempotency_key`) 한 곳이다. 장바구니에 "주문됨" 상태를 기록하지 않는다([ADR-0003](0003-cart-in-redis-with-ttl.md)의 판단 유지).

### 키 전달 방식

- 서버 → 클라이언트: 장바구니 응답 본문의 `idempotencyKey` 필드로 내려준다. 키는 장바구니 상태의 일부다.
- 클라이언트 → 서버: 주문·결제 요청에서는 `Idempotency-Key` 요청 헤더로 보낸다. 본문에 넣지 않는다.
- 헤더로 받는 이유:
  - 멱등키는 "이 요청이 재시도인가"를 알려주는 요청 메타데이터다. 본문은 주문·결제 내용만 담는다.
  - 이후 단계에서 키 선점, 저장된 응답 재반환, 처리 중 중복 요청 차단을 필터·인터셉터 하나로 실험한다. 헤더에 있으면 본문을 파싱하기 전에, 엔드포인트와 관계없이 같은 방식으로 꺼낼 수 있다.
  - IETF `Idempotency-Key` 헤더 초안과 주요 결제 API의 관행과 같고, 본문이 없는 요청에도 똑같이 적용된다.
- `POST /cart`는 요청 자체가 전체 교체라 멱등하므로 `Idempotency-Key` 헤더를 받지 않는다.

## 고려한 대안

### 대안 1: 요청마다 클라이언트가 새 멱등키를 만든다 (주문 키, 결제 키를 각각)

- 장점: 일반적인 HTTP 멱등키 관행(Stripe 등)과 같다.
- 단점: 주문과 결제의 연결은 주문 ID로 따로 해야 하고, 클라이언트가 키 생성·보관 책임을 진다. 장바구니에서 결제까지 하나의 흐름으로 추적하기 어렵다.

채택하지 않는다.

### 대안 2: 주문 생성 시점에 키를 발급한다

- 장점: 장바구니가 멱등성을 몰라도 된다.
- 단점: 주문 생성 요청 자체의 재시도를 구분할 수 없다. 키를 받기 전에 응답이 유실되면 재시도가 새 주문을 만든다.

채택하지 않는다.

### 대안 3: 장바구니에서 발급한 키를 주문·결제까지 사용

- 장점: 첫 주문 요청 전에 키가 이미 클라이언트에 있어 주문 생성부터 재시도에 안전하다. 장바구니·주문·결제를 한 값으로 추적할 수 있다.
- 단점: 장바구니 수명(TTL)과 키 수명이 묶인다. 주문 전에 장바구니가 만료되면 키가 바뀐다.

채택한다.

### 대안 4: 주문·결제 요청 본문에 키를 넣는다 (`{ "checkoutKey": ... }`)

- 장점: 이 키는 `orders.idempotency_key`로 저장되는 도메인 값이기도 하므로, 비즈니스 필드로 다루는 것도 자연스럽다.
- 단점: 공통 멱등성 처리를 만들려면 API마다 본문 DTO를 열어 봐야 한다. 표준 헤더 관행과 다르다.

채택하지 않는다.

## 결과

- 장바구니 응답에 `idempotencyKey`가 추가된다. 주문·결제 요청은 이 값을 `Idempotency-Key` 헤더로 보낸다.
- 주문 전 TTL 만료나 비우기로 키가 바뀌는 것은 정상 동작이다. 아직 주문이 없으므로 중복 위험이 없다.
- 키가 장바구니(Redis)와 주문(RDB)에 나뉘어 있어, 주문 커밋 후 장바구니 삭제가 실패하면 같은 키를 가진 장바구니가 남을 수 있다. 이때 고객이 장바구니를 바꿔 다시 주문하면 기존 주문이 반환된다. 처리 방식(주문된 키를 가진 장바구니는 새 키로 다시 시작 등)은 주문 스펙에서 정한다.
- 동시 요청에서의 키 충돌(같은 키로 주문 두 건이 동시에 들어옴)은 unique 제약으로 중복만 막고, 응답 정리는 이후 재현 대상으로 남긴다([PRD 8. 알려진 한계](../prd.md#8-알려진-한계)).
