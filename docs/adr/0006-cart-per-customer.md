# ADR-0006: 장바구니를 고객별로 하나 두고 Redis Hash에 저장

- 상태: 제안됨 (검토 중)
- 일자: 2026-10-13
- 관계: [ADR-0002](0002-cart-checkout-creates-order.md)를 대체한다. [ADR-0003](0003-cart-in-redis-with-ttl.md)의 "Cart는 Redis에 TTL과 함께 저장한다"는 유지하고, 키(`cart:{idempotencyKey}`)와 JSON 값 형식, 주문 여부 판단 규칙을 대체한다.

## 맥락

이전 설계의 Cart는 멱등키로 식별되는 주문 초안이었다. 클라이언트가 `orderLines` 전체를 매번 보내 교체했고, 같은 키가 주문 생성 재시도 키 역할도 했다. 이 구조는 장바구니가 아니라 주문 요청에 가깝고, 상품을 하나씩 담고 수량을 바꾸는 일반적인 장바구니 사용 흐름을 표현하지 못한다.

장바구니와 주문을 분리하면 장바구니 API를 먼저 단독으로 완성하고, 주문 생성 규칙은 주문 스펙에서 따로 정할 수 있다.

## 결정

- 장바구니는 고객당 하나다. 고객은 `X-Customer-Id` 요청 헤더로 식별한다. 인증은 이 단계에서 다루지 않는다.
- Redis 키는 `cart:{customerId}`이고 값은 Hash다. 필드는 상품 ID, 값은 수량이다.
- 상품명·가격은 저장하지 않는다([ADR-0005](0005-product-api-mock-catalog.md)).
- 쓰기마다 TTL(`payment-playground.cart.ttl`, 기본 7일)을 다시 설정한다. 마지막 상품이 빠지면 키를 삭제한다.
- 장바구니 API는 상품 담기, 수량 변경, 상품 빼기, 조회, 비우기만 제공한다. 장바구니에서 주문을 만드는 규칙과 멱등키는 주문 스펙에서 정한다.

## 고려한 대안

### 대안 1: 멱등키 기반 주문 초안 유지 (ADR-0002·0003)

- 장점: 이미 문서화되어 있고, 주문 생성 재시도까지 한 키로 처리한다.
- 단점: 장바구니 조작 API가 없고, 장바구니와 주문 생성의 책임이 섞인다.

채택하지 않는다.

### 대안 2: 고객별 장바구니를 JSON 문자열 하나로 저장

- 장점: 담은 순서나 추가 시각 같은 필드를 함께 보관하기 쉽다.
- 단점: 매 변경마다 전체를 읽고 직렬화해 다시 써야 한다. 상품 ID → 수량만 필요한 지금은 Hash보다 이점이 없다.

채택하지 않는다.

### 대안 3: 고객별 장바구니를 SQLite에 저장

- 장점: 다른 데이터와 같은 트랜잭션으로 다룰 수 있다.
- 단점: 만료를 직접 구현해야 한다(ADR-0003의 판단과 같다).

채택하지 않는다.

## 결과

- 장바구니 응답의 상품 순서는 저장되지 않으므로 상품 ID 오름차순으로 고정한다.
- 이 단계의 장바구니 변경은 "Hash 읽기 → 애플리케이션에서 계산 → 키 삭제 후 다시 쓰기"다. 원자적이지 않으므로 동시 변경 시 하나가 사라질 수 있다. 이는 의도한 한계이며 이후 재현 대상이다([PRD 알려진 한계](../prd.md#8-알려진-한계)).
- 주문이 장바구니를 어떻게 소비할지(주문 후 비우기, 주문 시 가격 스냅샷, 주문 멱등키)는 주문 스펙과 새 ADR에서 결정한다.
