# ADR-0006: 장바구니를 고객별로 하나 두고 전체 교체 방식으로 저장

- 상태: 제안됨 (검토 중)
- 일자: 2026-10-13
- 관계: [ADR-0002](0002-cart-checkout-creates-order.md)를 대체한다. [ADR-0003](0003-cart-in-redis-with-ttl.md)의 "Cart는 Redis에 TTL과 함께 저장한다"는 유지하고, 키(`cart:{idempotencyKey}`)와 주문 여부 판단 규칙을 대체한다. 멱등키의 발급과 사용 범위는 [ADR-0007](0007-checkout-idempotency-key.md)에서 정한다.

## 맥락

이전 설계의 Cart는 멱등키로 식별되는 주문 초안이었다. 클라이언트가 멱등키를 들고 다니며 Cart를 찾아야 했고, 같은 키가 Cart의 식별자이자 주문 생성 재시도 키였다. 실제 서비스에서 장바구니는 "로그인한 고객의 장바구니"로 찾는 것이 자연스럽다.

장바구니 변경 API를 담기·수량 변경·빼기·비우기로 나누면 엔드포인트와 오류 경우가 늘어난다. 클라이언트는 이미 화면에 장바구니 전체 상태를 들고 있으므로, 그 상태를 통째로 보내는 편이 단순하다.

## 결정

- 장바구니는 고객당 하나다.
- 고객 ID는 Controller 파라미터 `@CurrentCustomer customerId: String`으로 받는다. 지금은 `X-Customer-ID` 요청 헤더를 읽는 resolver로 구현하고, 인증이 생기면 인증 정보에서 꺼내는 resolver로 교체한다. Controller와 Service는 헤더 이름을 알지 못한다.
- API는 `GET /cart`(조회)와 `POST /cart`(전체 교체 저장) 두 개다. 빈 목록 저장이 비우기다.
- Redis 키는 `cart:{customerId}`, 값은 `customerId`, `idempotencyKey`, `items`(상품 ID와 수량), `createdAt`, `updatedAt`을 가진 JSON 문자열 하나다. 저장은 `SET ... EX` 한 명령이다.
- 상품명·가격은 저장하지 않는다([ADR-0005](0005-product-api-mock-catalog.md)).
- TTL은 `payment-playground.cart.ttl`(기본 30분)이고 저장마다 다시 설정한다. 조회는 TTL을 연장하지 않는다.

## 고려한 대안

### 대안 1: 멱등키 기반 주문 초안 유지 (ADR-0002·0003)

- 장점: 이미 문서화되어 있다.
- 단점: 클라이언트가 키로 장바구니를 찾아야 하고, 장바구니 식별과 주문 재시도 키가 한 개념에 섞인다.

채택하지 않는다.

### 대안 2: 항목 단위 API (`POST /cart/items`, `PATCH`/`DELETE /cart/items/{id}`, `DELETE /cart`)

- 장점: 요청이 작고, 변경 의도가 API에 드러난다.
- 단점: 엔드포인트와 오류 경우(담기지 않은 상품 변경 등)가 늘고, 서버가 "기존 수량 + 추가 수량" 같은 계산을 맡는다. 같은 요청을 재시도하면 수량이 두 번 더해질 수 있어 요청 자체가 멱등이 아니다.

채택하지 않는다.

### 대안 3: Redis Hash(상품 ID → 수량)

- 장점: 항목 단위 변경(`HINCRBY`)에 잘 맞는다.
- 단점: 전체 교체에서는 "삭제 → 필드 쓰기 → TTL" 세 명령이 필요해 원자적이지 않다. 멱등키·생성 시각 같은 장바구니 단위 필드를 상품 필드와 섞어야 한다.

채택하지 않는다.

### 대안 4: 고객 ID를 Controller에서 헤더로 직접 읽기

- 장점: 코드가 가장 짧다.
- 단점: 인증 도입 시 모든 Controller를 고쳐야 한다.

채택하지 않는다.

## 결과

- `POST /cart`는 같은 본문을 여러 번 보내도 결과가 같다. 재시도에 안전하다.
- 저장이 한 명령이라 "쓰는 도중의 빈 장바구니"나 "TTL 없는 키"가 생기지 않는다.
- 같은 고객의 동시 저장은 나중 요청이 이긴다(last write wins). 각 요청이 전체 상태를 보내므로 "변경 일부 유실"이 아니라 "한 쪽 화면 상태가 통째로 덮임"이 된다. 이는 의도한 한계다([PRD 8. 알려진 한계](../prd.md#8-알려진-한계)).
- 장바구니에 담을 수 있는 상품 수만큼 요청 본문이 커진다. 이 프로젝트 규모에서는 문제가 되지 않는다.
- 고객 ID를 헤더로 믿으므로 다른 고객의 장바구니를 바꿀 수 있다. 인증 도입 시 resolver 교체로 해결한다.
