# 코드 컨벤션

> 상태: 승인됨 · 작성일: 2026-10-16 · 최종 갱신일: 2026-10-16

> 문서 역할과 갱신 원칙은 [문서 가이드](README.md)를 따른다. 이 문서는 기능 코드를 어떤 계층과 파일로 나누고, 계층 사이에 어떤 타입을 주고받는지 정한다. 새 기능의 스펙 "패키지와 책임" 절은 이 규칙을 따른다.

## 1. 패키지와 기능 사이 의존

- 기능별 패키지를 둔다: `product`, `cart`, `order`(이후 `payment`). 한 기능의 컨트롤러·서비스·도메인·저장소는 같은 패키지에 있다.
- `customer`: 현재 고객을 알아내는 웹 계층 장치(`@CurrentCustomer`, resolver). 기능이 아니라 요청 컨텍스트다.
- `support`: 특정 기능에 속하지 않는 기술 요소. 시간(`Clock`), ID·키 생성(`IdempotencyKeyGenerator`), 공통 오류 타입과 오류 응답, 공통 변환기. 비즈니스 규칙을 넣지 않는다. `support`는 어떤 기능 패키지에도 의존하지 않는다.

### 1.1 기능 사이 의존은 순환하지 않는다

기능 사이 의존은 한 줄로 서는 순서가 아니라 **순환이 없는 그래프**다. 한 기능이 여러 기능에 의존해도 되지만, 의존을 따라가다 자기 자신으로 돌아오면 안 된다.

```text
product ◀── cart ◀── order ◀── (payment)
   ▲                   │
   └───────────────────┘
```

- 방향은 비즈니스 흐름으로 정한다. 흐름의 **뒤 단계가 앞 단계에 의존**한다(주문은 장바구니를 알지만, 장바구니는 주문을 모른다).
- 순환을 막는 이유: 순환이 생기면 두 기능을 따로 바꾸거나 테스트할 수 없고, Spring 빈 순환 참조가 생기며, 이후 기능을 모듈·서비스로 떼어 내는 실험을 할 수 없다.
다른 기능에 접근하는 방법은 읽기와 변경으로 나눈다.

- **읽기:** 다른 기능의 데이터를 읽기만 할 때는 그 기능의 **저장소 인터페이스**(예: `ProductRepository`)와 그것이 돌려주는 도메인 모델을 쓸 수 있다. 받은 도메인 모델은 읽기만 하고, 다른 기능 쪽에서 고치거나 저장하지 않는다.
- **규칙이 걸린 읽기:** 읽기라도 그 기능의 규칙이 걸리면(어떤 상품을 판매 중으로 볼지, 장바구니를 어떤 모양으로 주문에 넘길지 등) 그 기능의 **서비스**를 거친다. 처음에는 저장소로 읽다가 규칙이 생기면 그때 서비스로 옮긴다.
- **변경:** 다른 기능의 상태를 바꾸는 일(저장, 삭제, 상태 전이)은 항상 그 기능의 **서비스**를 거친다. 예: 주문은 장바구니를 `CartService.clear`로 지운다.
- 쓰지 않는 것: 다른 기능의 저장소 **구현 클래스**(예: `RedisCartRepository`, `FixedProductRepository`), 컨트롤러, HTTP 계약 타입(`Request`·`Response`).
- 이유: 상태 변경에는 그 기능의 규칙(예: 장바구니를 지우면 멱등키도 사라진다)이 걸려 있어 저장소로 직접 바꾸면 그 규칙을 건너뛴다. 순수한 조회는 저장소로 읽어도 잃는 것이 없고, 캐시도 저장소 계층에서 처리할 수 있다(3.1).

### 1.2 앞 단계가 뒤 단계의 정보가 필요할 때

흐름의 앞 기능이 뒤 기능을 알아야 할 것 같으면(예: 장바구니가 "이 키로 이미 주문이 있는가"를 알아야 하는 경우), 의존을 거꾸로 만들지 않고 다음 중 하나로 푼다. 위에서부터 먼저 검토한다.

1. **뒤 기능이 처리한다.** 뒤 기능의 서비스가 앞 기능을 호출해 필요한 일을 한다. 현재 주문 재호출 때 남은 장바구니를 주문 서비스가 정리하는 방식이다.
2. **의존성 역전.** 앞 기능이 필요한 질문을 인터페이스로 선언하고(예: `cart`의 `OrderedCheckoutKeys`), 뒤 기능이 구현한다. 실행 중 호출은 앞 → 뒤지만 코드 의존은 여전히 뒤 → 앞이다.
3. **이벤트.** 뒤 기능이 이벤트를 발행하고 앞 기능이 받는다. 이벤트 타입은 받는 쪽 패키지나 `support`에 둔다. 발행하는 쪽에 두면 받는 쪽이 그 패키지를 import해 순환이 생긴다.

어느 방법을 썼는지는 해당 기능 스펙의 "패키지와 책임" 절에 적는다.

## 2. 계층과 계층 사이의 타입

```text
[HTTP] ── XxxRequest ──▶ Controller ── XxxCommand ──▶ Service ──▶ Repository
                            │                          │   ◀── 엔티티 ──┘
[HTTP] ◀── XxxResponse ─────┘ ◀──────── XxxResult ─────┘
```

각 계층은 자기가 받는 입력과 내보내는 출력 타입을 스스로 선언한다. 의존은 아래로만 향한다.

### 2.1 계층 사이 의존

| 계층 | 의존할 수 있는 것 | 의존하지 않는 것 |
| --- | --- | --- |
| Controller | 같은 기능의 서비스, `customer`, `support` | 저장소, 엔티티·도메인 모델, 다른 기능의 서비스 |
| Service | 같은 기능의 도메인 모델·저장소, 다른 기능의 서비스, 다른 기능의 저장소 인터페이스(읽기 전용, 1.1), `support` | 다른 기능의 저장소 구현, 다른 기능 데이터의 직접 변경, 컨트롤러, `Request`·`Response`, HTTP 타입(`ResponseEntity`, `HttpStatus`, 헤더) |
| Repository | 도메인 모델·엔티티, 저장 기술(JPA, Redis), `support` | 서비스, 컨트롤러 |
| 도메인 모델·엔티티 | 같은 기능의 다른 도메인 타입, `support`의 값 타입 | 서비스, 저장소, 컨트롤러, Spring 빈 |

- **건너뛰지 않는다.** 컨트롤러가 저장소를 직접 부르지 않는다. 로직이 없는 조회도 서비스를 거친다(상품 조회 포함).
- **위로 부르지 않는다.** 아래 계층이 위 계층에 알리는 방법은 반환값(서비스는 `Result`, 저장소는 엔티티·도메인 모델)과 예외뿐이다. 콜백이나 위 계층 빈 주입으로 거꾸로 부르지 않는다.
- **오류는 도메인 예외로 올린다.** 서비스는 `support`의 `DomainException` 하위 타입을 던지고, HTTP 상태 코드로 바꾸는 일은 `ApiExceptionHandler`가 한다. 서비스는 상태 코드를 모른다.
- **트랜잭션 경계는 서비스다.** `@Transactional`이나 `TransactionTemplate`은 서비스에만 둔다. 컨트롤러와 저장소 구현은 트랜잭션을 시작하지 않는다(Spring Data가 기본으로 제공하는 메서드 단위 트랜잭션은 예외).
- **도메인 모델은 아래를 모른다.** 엔티티의 JPA 매핑 애노테이션은 허용하지만, 도메인 모델이 저장소나 서비스를 호출하지 않는다. 규칙 검증(`require`)과 계산은 도메인 모델 안에 둔다.
- **같은 계층끼리:** 서비스는 다른 기능의 서비스를 부를 수 있다(1.1의 방향을 따른다). 컨트롤러는 다른 컨트롤러를 부르지 않는다.

| 계층 | 선언하는 타입 | 아는 타입 | 모르는 타입 |
| --- | --- | --- | --- |
| Controller | `XxxRequest`, `XxxResponse` | 서비스의 `XxxCommand`·`XxxResult` | 엔티티·도메인 모델, 저장소 |
| Service | `XxxCommand`, `XxxResult` | 엔티티·도메인 모델, 저장소 | `Request`·`Response`, HTTP(헤더, 상태 코드) |
| Repository | (엔티티·도메인 모델을 다룬다) | 엔티티·도메인 모델 | 위의 모든 것 |

### 2.2 들어오는 방향

- `XxxRequest`: HTTP 본문의 모양과 Bean Validation 애노테이션을 가진다. 컨트롤러 밖으로 나가지 않는다.
- 컨트롤러는 검증이 끝난 요청을 `XxxCommand`로 바꿔 서비스에 넘긴다. 서비스 입력이 ID나 헤더 값 몇 개뿐이면 `Command`를 만들지 않고 값으로 넘긴다.
- 헤더 공백 제거처럼 HTTP 입력을 정리하는 일은 컨트롤러(또는 `customer` resolver)가 한다.

### 2.3 나가는 방향

- 서비스는 저장소에서 엔티티·도메인 모델을 받아 비즈니스 로직을 수행하고, 그 결과를 `XxxResult`로 만들어 반환한다. **엔티티·도메인 모델을 서비스 밖으로 반환하지 않는다.**
  - 이유: `spring.jpa.open-in-view=false`라서 트랜잭션 밖에서는 지연 로딩 필드를 읽을 수 없다. `Result`는 트랜잭션 안에서 필요한 값을 모두 읽어 둔 값이다. 또 테이블 구조와 API 응답이 서로를 끌고 다니지 않게 한다.
  - 응답 분기에 필요한 서비스 판단(예: 새로 만들었는지 재호출인지)도 `Result`에 담는다.
- 컨트롤러는 `XxxResponse.from(result)`로 응답을 만들고 상태 코드·헤더(`Location` 등)를 정한다.
- `Result`와 `Response`의 필드가 지금 같더라도 두 타입을 합치지 않는다.

### 2.4 이름

| 종류 | 이름 | 예 |
| --- | --- | --- |
| HTTP 요청 본문 | `<동작><대상>Request` | `SaveCartRequest`, `SaveCartLineRequest` |
| HTTP 응답 본문 | `<대상>Response` | `CartResponse`, `OrderLineResponse` |
| 서비스 입력 | `<대상>Command` | `CartLineCommand` |
| 서비스 출력 | `<대상>Result`, 동작 결과는 `<동작><대상>Result` | `CartResult`, `PlaceOrderResult` |
| 도메인 모델·엔티티 | 접미사 없음 | `Cart`, `Order`, `OrderLine`, `Product` |

`View`, `Dto`, `Info` 같은 접미사는 쓰지 않는다.

## 3. 파일

기능 패키지 안의 파일은 역할별로 나눈다.

| 파일 | 내용 |
| --- | --- |
| `XxxController.kt` | 컨트롤러 |
| `XxxApi.kt` | 그 기능의 HTTP 계약: `Request`·`Response`와 `Response.from(...)`. 스펙의 요청·응답 절과 1:1로 대응한다. |
| `XxxService.kt` | 서비스와 그 `Command`·`Result` |
| `Xxx.kt` | 도메인 모델·엔티티(필요하면 관련 enum·값 타입) |
| `XxxRepository.kt` | 저장소 인터페이스(또는 Spring Data 인터페이스)와 저장소가 반환하는 값 타입 |
| `<기술>XxxRepository.kt` | 저장소 구현과, 그 구현만 아는 저장 형식(직렬화용 문서 클래스·인코딩 함수는 `private`) |
| `XxxErrors.kt` | 그 기능의 도메인 오류를 만드는 함수(`productNotFound()` 등) |
| `XxxProperties.kt` | 그 기능의 설정(`@ConfigurationProperties`) |

- 저장 형식(예: Redis JSON 모양)은 저장소 구현의 세부 사항이다. 별도 코덱·문서 클래스를 공개 타입으로 두지 않는다.
- 저장소 인터페이스는 구현을 바꿔 끼우거나(테스트의 메모리 구현, 캐시 데코레이터 포함) 다른 기능이 구현이 아니라 계약으로 읽어야 할 때 둔다. Spring Data JPA 저장소는 인터페이스 자체가 계약이다.

### 3.1 캐시를 두는 위치

- **순수 캐싱은 저장소 계층:** 반환값이 항상 같은 도메인 엔티티·모델인 조회(예: ID로 상품 하나)는 같은 저장소 인터페이스를 구현하는 데코레이터로 캐싱한다(예: `CachingProductRepository`가 `ProductRepository`를 구현하고 DB 저장소를 감싼다). 쓰는 쪽은 캐시 여부를 모른다.
- **조합·유스케이스별 캐싱은 서비스 계층:** 여러 저장소의 값을 조합한 결과를 캐싱하거나, 화면·유스케이스마다 TTL·최신성 요구가 다르면 서비스가 캐시를 정한다.

## 4. 서비스 나누기

기능마다 서비스 하나(`XxxService`)로 시작한다. 다음 중 하나에 해당하면 나눈다.

- 성격이 다른 호출자(컨트롤러, 다른 기능, 배치 등)가 둘 이상이고 그 요구가 갈라지기 시작했다.
- public 메서드가 6개를 넘거나 생성자 의존성이 5개를 넘는다.

나누는 순서:

1. 먼저 계산·판단을 도메인 모델(또는 작은 도메인 객체)로 옮길 수 있는지 본다. 서비스는 "읽고, 도메인에 시키고, 저장한다"는 흐름만 남기는 것이 목표다.
2. 그래도 크면 유스케이스별로 나눈다: `<동작><대상>Service`(예: `PlaceOrderService`, `GetOrderService`).
3. 다른 기능에 공개하는 범위를 좁혀야 하면 그 용도의 진입점을 따로 둔다: `<대상>Reader`, `<대상>Provider` 등 역할을 드러내는 이름(예: `CheckoutCartReader`). `XxxApi`는 HTTP 계약 파일 이름이므로 쓰지 않는다.

나눈 뒤에도 1·2장의 규칙(엔티티를 밖으로 내보내지 않음, `Command`·`Result`로 주고받음)은 그대로다.

## 5. 테스트

- 테스트는 대상 계층의 타입으로 단언한다: 컨트롤러 테스트는 JSON 응답(필드 이름·값·상태 코드), 서비스 테스트는 `Result`, 저장소 테스트는 저장된 값.
- 여러 기능이 함께 쓰는 테스트 지원 코드는 테스트 소스의 `support` 패키지에 둔다(예: 순서대로 키를 만드는 `SequentialIdempotencyKeyGenerator`). 한 기능만 쓰면 그 기능의 `XxxTestFixtures.kt`에 둔다.

## 6. 예외로 두는 것

없다. 로직이 없는 읽기 전용 기능(현재 상품)도 `Service`·`Result`를 둔다. 기능이 커질 때 계층을 나중에 끼워 넣는 비용보다, 모든 기능이 같은 모양인 이점이 크다고 본다.
