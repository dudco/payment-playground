# 주문·결제 API PRD

> 문서 역할과 갱신 원칙은 [문서 가이드](README.md)를 따른다. 기능별 구현 상세는 [기능 스펙](specs/), 공유 영속 규칙은 [데이터 모델](data-model.md)을 기준으로 한다.

## 1. 목적

`payment-playground`는 상품을 장바구니에 담고, 주문하고, 결제하는 API를 만든 뒤 대용량 트래픽에서 생기는 문제(동시성, 정합성, 배치 처리)를 하나씩 재현하고 해결하는 실험 프로젝트다. REST API와 자동 테스트만 제공하며, UI와 실제 PG/VAN 네트워크 통신은 범위에 포함하지 않는다.

현재 단계의 목표는 **트래픽이 거의 없는 환경에서 올바르게 동작하는 최소 MVP**다. 속도나 트래픽 대응을 위한 장치(락, 큐, 캐시 전략, 재시도 등)는 넣지 않는다. 대신 막지 않는 문제를 [8. 알려진 한계](#8-알려진-한계)에 기록하고, 이후 단계에서 재현한 뒤 해결한다.

## 2. 용어와 명명 규칙

| 용어 | 코드 명명 | 의미 |
| --- | --- | --- |
| 상품 | `Product` | 고객에게 판매하는 카탈로그 단위. 판매명·판매가의 기준이다. 현재는 Mock 카탈로그로 제공한다. |
| 품목 | `Item` | 매입·재고 관리 단위. 하나의 `Product`에 여러 `Item`이 연결될 수 있다. 현재 구현하지 않는다. |
| 장바구니 | `Cart` | 고객이 주문 전에 상품과 수량을 모아 두는 고객별 임시 데이터. Redis에 TTL과 함께 저장한다. |
| 체크아웃 멱등키 | `idempotencyKey` | 장바구니가 처음 저장될 때 서버가 발급하는 값. 장바구니 → 주문 → 결제로 이어지는 한 번의 구매 흐름을 식별한다([ADR-0007](adr/0007-checkout-idempotency-key.md)). |
| 주문 | `Order` | 구매 의사와 결제 대상의 불변 기록. 주문 스펙에서 정의한다. |
| 주문 라인 | `OrderLine` | 주문 시점의 상품·수량·판매가 스냅샷. 주문 스펙에서 정의한다. |
| 결제 | `Payment` | 특정 주문에 대한 한 번의 결제 시도. 결제 스펙에서 정의한다. |

장바구니에 담긴 "상품 + 수량" 한 줄은 **장바구니 라인**(`lines`의 원소)이라 부른다. 별도 엔티티·테이블을 만들지 않고 장바구니 JSON 안의 값으로만 둔다. 주문 시 `OrderLine`으로 옮겨지는 단위다. `items`·`CartItem`이라는 이름은 `Item`(품목)과 혼동되므로 쓰지 않는다. `OrderItem`도 사용하지 않는다.

## 3. 단계별 범위

기능은 스펙 단위로 하나씩 추가한다. 각 기능은 스펙이 승인된 뒤 구현한다.

| 순서 | 기능 | 상태 | 문서 |
| --- | --- | --- | --- |
| 1 | 상품 조회 (Mock) | 구현 완료 | [상품 조회 API 명세](specs/product-api.md), [ADR-0005](adr/0005-product-api-mock-catalog.md) |
| 1 | 장바구니 | 구현 완료 | [장바구니 API 명세](specs/cart-api.md), [ADR-0006](adr/0006-cart-per-customer.md), [ADR-0007](adr/0007-checkout-idempotency-key.md) |
| 2 | 주문 생성 | 예정 | 장바구니의 멱등키로 주문을 만들고 가격을 스냅샷한다. 같은 키 재호출은 기존 주문을 반환한다. |
| 3 | 결제 | 예정 | 같은 멱등키로 결제를 요청한다. 온라인 카드·오프라인 카드·자체 포인트를 결제수단별 Gateway로 처리한다([ADR-0001](adr/0001-payment-gateway-by-method.md)). |

## 4. 현재 단계 목표와 비범위

### 목표

- 서버가 정한 상품 목록과 판매가를 조회할 수 있다.
- 고객은 장바구니 전체 상태를 저장(`POST /cart`)하는 방식으로 상품을 담고, 수량을 바꾸고, 빼고, 비울 수 있다.
- 장바구니가 처음 저장될 때 체크아웃 멱등키가 발급되고, 장바구니가 있는 동안 유지된다.
- 장바구니 금액은 서버가 상품 카탈로그의 현재 판매가로 계산한다. 클라이언트가 보낸 가격을 받지 않는다.
- 마지막 저장 후 30분이 지난 장바구니는 자동으로 사라진다.

### 비범위

- 주문·결제(다음 스펙)
- 상품 등록·수정, 재고, `Item` 모델
- 인증·인가. 고객 ID는 임시로 `X-Customer-ID` 헤더 값을 그대로 믿는다. 인증이 생기면 인증 정보에서 꺼내도록 교체한다([ADR-0006](adr/0006-cart-per-customer.md)).
- 비회원 장바구니, 장바구니 병합, 쿠폰·할인
- 동시 요청 제어(락, 원자적 연산, 낙관적 버전)

## 5. 사용자 흐름

1. 클라이언트는 `GET /products`로 상품 목록을 본다.
2. 고객이 상품을 담으면 클라이언트는 장바구니 전체(`lines`)를 `POST /cart`로 보낸다. 첫 저장이면 서버가 멱등키를 발급한다.
3. 수량을 바꾸거나 상품을 빼도 변경된 전체 목록을 다시 `POST /cart`로 보낸다. 멱등키는 그대로다.
4. `GET /cart`로 담긴 상품, 상품별 금액, 총액, 멱등키, 만료 시각을 본다.
5. 빈 목록을 `POST /cart`로 보내면 장바구니가 비워지고 멱등키도 사라진다.
6. 마지막 저장 후 TTL(기본 30분)이 지나면 장바구니와 멱등키가 사라지고, 조회하면 빈 장바구니가 된다.
7. (다음 단계) 클라이언트는 응답의 멱등키를 `Idempotency-Key` 헤더로 주문·결제 요청에 보낸다.

## 6. 공통 계약

- 오류 본문은 `{ "code": "...", "message": "..." }`다.
- `400 VALIDATION_ERROR`: 필수 헤더·본문 누락, 형식 오류, 범위 밖 값
- `404`: 대상 상품이 없음
- `409`: 현재 상태에서 허용되지 않는 요청 (현재 단계에서는 사용하지 않음)
- `422`: 형식은 맞지만 비즈니스 규칙 위반
- 금액은 KRW 정수다.

## 7. 보안 및 개인정보 정책

저장 및 로그 금지: 원문 카드번호, Track2 원문, PIN, 주민번호, OTC, OTC2, XID, ECI, CAVV, 서명 바이너리, 원본 VAN 전문, PG 토큰, 포인트 바코드 원문.

이 규칙은 RDB, Redis, API 응답, 애플리케이션 로그 모두에 적용한다. 검증 오류 응답에는 거부된 입력값을 싣지 않는다. 결제 데이터의 보존 대상은 결제 스펙에서 정한다.

## 8. 알려진 한계

이 단계는 요청이 한 번에 하나씩 들어온다고 가정한다. 아래 항목은 의도적으로 막지 않으며, 이후 단계의 재현 대상이다. 해결할 때는 해당 항목을 재현하는 테스트를 먼저 작성한다.

- **같은 고객의 동시 장바구니 저장 → 나중 요청이 이긴다.** `POST /cart`는 전체 교체라 두 화면(예: 앱과 웹)에서 동시에 저장하면 한 쪽 상태가 통째로 덮인다. 버전 검사가 없으므로 클라이언트는 덮인 사실을 알 수 없다.
- **첫 저장 경합 → 멱등키가 바뀔 수 있다.** 장바구니가 없을 때 같은 고객의 첫 `POST /cart` 두 개가 동시에 오면 둘 다 "없음"을 읽고 각자 키를 발급한다. 나중 요청의 키가 남고, 먼저 받은 응답의 키는 더 이상 유효하지 않다. 주문 전이므로 중복 주문으로 이어지지는 않는다.
- **고객 식별을 헤더로 믿는다.** 다른 고객의 ID를 보내면 그 장바구니를 바꿀 수 있다. 인증이 들어오면 해결한다.
- **장바구니 가격은 고정되지 않는다.** 상품 가격이 바뀌면 다음 조회부터 새 가격이 보인다. 가격 확정은 주문 시점의 책임이다.
- **자동 테스트는 실제 Redis를 쓰지 않는다.** Redis 명령 호출과 인자, JSON 왕복, TTL 계산만 검증한다. Redis 버전 차이나 직렬화 설정이 실제 서버에서만 드러나는 문제는 수동 확인에 맡긴다. 동시성 재현 단계에서 실제 Redis 테스트를 추가한다.
- **주문 직전 만료.** 결제 페이지에 30분 넘게 머무르면 장바구니와 멱등키가 사라진다. 주문 스펙에서 만료된 키로 주문 요청이 오면 어떻게 응답할지 정한다.

## 9. 수용 조건

- 상품 목록과 단건을 조회할 수 있고, 없는 상품은 `404 PRODUCT_NOT_FOUND`다.
- 장바구니 저장·조회와 멱등키 발급·유지가 [장바구니 API 명세](specs/cart-api.md#7-테스트-수용-조건)의 수용 조건을 자동 테스트로 만족한다.
- 장바구니 금액은 서버 카탈로그 가격으로만 계산된다.
- 장바구니 저장 시 설정값 TTL(기본 30분)을 담은 Redis 명령이 실행된다. 자동 테스트는 Redis 없이 실행한다.
